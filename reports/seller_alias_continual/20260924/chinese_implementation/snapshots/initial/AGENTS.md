Read [the research disciplines](docs/RESEARCH_DISCIPLINE.zh.md) and the current section of [the research handoff](docs/AI_RESEARCH_HANDOFF.zh.md) before changing a research step. This file summarizes current execution rules; historical progress belongs in the handoff and existing reports. The user's latest explicit instruction takes precedence within its stated scope. If the applicable requirement remains unclear, ask the user instead of silently choosing an interpretation.

## Clarify Research Instructions

When research instructions are vague, broad, or contradictory, proactively ask for the missing details before advancing dependent work. Use the conversation and confirmed plan to identify actual gaps in the research question, expected output, scope, data and label boundaries, comparison, resource budget, or decision criteria. Explain the consequences of the choices; do not treat assumptions as confirmed requirements or impose a fixed questionnaire.

A request to continue an already clear, confirmed plan allows execution within that plan. Ask before proceeding with an unconfirmed research question, dataset, comparison method, training budget, or evaluation standard. Clear implementation errors within the confirmed plan may be minimally fixed, verified, and reported directly. While awaiting answers, read documentation, inspect existing evidence, and prepare concrete proposals; defer implementation, data processing, and experiments that depend on unresolved requirements. Record the user's answers and scope in the relevant plan or handoff, and reconcile affected rules here and in the research disciplines.

## Project Structure and File Naming

This is a step-numbered Python research pipeline. Put executable experiments in `scripts/`, contract and regression tests in `tests/`, machine-readable policies in `schema/`, research plans and conclusions in `docs/`, and reproducible outputs in `reports/`. Model payloads live under `models/`. Root marketplace exports, `html-rips/`, and dated source dumps are immutable inputs. Use names such as `step24_build_pair_features.py`; when a persistent Linux orchestration script is needed, use `run_step*_linux_YYYYMMDD.sh`.

Use four-space indentation, `snake_case`, `UPPER_CASE` constants, type hints for nontrivial interfaces, and `pathlib.Path`. Prefer deterministic sorting, fixed seeds, explicit schemas, and fail-closed validation. Write UTF-8 JSON/JSONL and preserve established CSV encodings.

File basenames must be short, describe their purpose, and contain no version numbers. Steps, scientific quantities, seeds, dates, and necessary language/format suffixes are not versions. Keep existing experiment directory identifiers. Use a distinct new run directory for new results; never overwrite a published artifact with different bytes or merge independent experiments. Update document references, imports, and commands together. Preserve scientific version fields, run IDs, model roles, and historical hashes. Frozen old paths resolve through `reports/file_naming_migration/20260905/filename_map.json`; a renamed reference does not make edited source bytes identical to the old snapshot.

Remove one-off helper scripts, review-upload copies, browser logs, caches, and temporary directories after use. Retain code and small records needed to reproduce valid research. Immutable review records and necessary scientific evidence are different from disposable upload copies. Before deleting an irrecoverably invalid run's payloads or run-specific code, document its ID, failure stage, root cause, claim boundary, critical hashes, and non-reuse commitments. Valid negative results remain research evidence. Never delete active experiment states as temporary clutter.

## Commands and Verification

There is no single build target. Inspect the relevant script's `--help` before execution. Choose checks for the actual change; these are examples, not a mandatory repeated sequence:

```powershell
python -B scripts/step28_continual_text_run.py --help
python -B -m unittest discover -s tests -p 'test_step28_continual_text_run_contracts.py'
```

Run affected tests for changed behavior, expanding coverage when changes cross module boundaries. A commit alone does not require full-suite execution. For pure documentation changes, check content, references, naming, and formatting only. Record commands, actual pass/skip counts, and limitations. Tests use `unittest` and names such as `test_step*_...contracts.py`. Do not run raw full discovery across permanently closed historical experiments; use an applicable partition if broader regression is justified. The old partitioning evidence is in `docs/STEP28_CURRENT_AND_HISTORICAL_REGRESSION_RESULT_20260830.zh.md`; its historical entry is `scripts/step28_regression_training.py`, not a mandatory check for the current mainline.

Before using inherited experiment code, read its implementation and direct scientific dependencies against the current research claim, equations, and contract. Frozen status, prior execution, passing tests, and external review do not establish implementation correctness. Apply the same responsibility to code you write. Check relevant data/label boundaries, model-visible inputs, split and sample alignment, objectives and weights, encoder/head gradients and updates, train/evaluation modes, paired budgets and randomness, checkpoint reload, metrics, and uncertainty.

Implementation review must establish that the actual computation performs the experiment the user requested. Start from the user's confirmed research question and approved intervention/comparison, independently of the code and executor-written policy, and trace each substantive requirement through actual inputs, training operations, outputs and evaluation. Agreement among code, tests, policies and logs is insufficient if all encode the same mistaken interpretation. Check whether the implemented comparison can answer the approved question and state what it cannot establish. Local and external reviews must identify the requirement, implementation evidence, deviations and remaining unverified behavior; test counts or “no blockers” alone are not the conclusion. Clarify any unresolved requirement with the user; do not redefine the request to match existing code or promise the desired empirical outcome.

Use hand-checkable cases or independent references and the smallest real runtime check needed for changed training semantics. Static checks, mocked outputs, or a nonzero combined gradient do not prove actual training correctness. Smoke is not a fixed stage ritual. Reuse verified evidence when semantics, relevant runtime conditions, and scientific boundaries are unchanged. Record reviewed files, affected claims, verification results, and remaining gaps; do not start dependent formal work while necessary verification is missing.

When taking over a step, read its directly relevant historical web-review texts and reconcile their reviewed scope and open/closed findings with current code. Local summaries alone are not a claim to have read the originals. Disclose unavailable originals and do not reopen resolved, unchanged findings merely because the executor changed.

Always scrutinize sub-agent reports. Before incorporating their work into a final report to the user, the primary executor must personally and carefully verify their claims against the relevant original documents, code, outputs and execution evidence. A sub-agent's confidence, completion status or reported test success is not proof. Correct confirmed errors and verify the corrections before reporting conclusions; clearly distinguish verified findings, proposals and unverified claims. Record the review scope, corrections and remaining limitations in the relevant existing research record. Delegation does not transfer final responsibility or expand data, experiment or resource authorization. Use checks appropriate to the affected claims, not automatic full reruns.

Close sub-agents promptly when their assigned tasks are complete, preserving necessary reports and evidence first. If the available tools cannot close a session, stop any remaining execution, verify its status and disclose the limitation; do not claim the session was closed.

## External Review and Scientific Scope

By default, use web ChatGPT GPT 6 Pro for substantive stage changes affecting the research plan, implementation, evaluation, or conclusions. Routine discipline/document organization, recording user decisions, renaming, link fixes, file copies, mechanical finalization, and unchanged evidence do not require external review unless they also change scientific substance. If the user explicitly instructs that an item or stage must not be submitted for external review, do not submit it within that stated scope. Record the exemption; local implementation and result verification still apply. Do not represent exempt work as externally reviewed. Preserve the actual model identity in historical review records.

The external reviewer advises; the local executor independently checks and decides on suggestions within the confirmed plan. Classify suggestions as `SCIENTIFIC_BLOCKER` (affecting scientific validity, data/label boundaries, inputs, splits, metrics, or conclusions), `REPRODUCIBILITY_DEFECT` (breaking replay or allowing ordinary file/result mismatch), or `OUT_OF_SCOPE_OVERDESIGN` (unrelated complexity or operating-system/network/attack hardening). Name the affected claim and use the smallest sufficient remedy for confirmed defects; reject unrelated complexity. Unconfirmed scientific choices go back to the user under the clarification rule. Disclose limitations without turning them into automatic blockers.

The research objective outranks process ceremony. Do not add private-key ceremonies, one-time signing, Linux Git requirements, network/system hardening, redundant state machines, or repeated review gates. Once the frozen command and direct output validation pass, record the result and advance within the confirmed plan; repeat checks or review only when a relevant change or unresolved concern justifies it.
