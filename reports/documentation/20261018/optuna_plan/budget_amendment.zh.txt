1. 用户指出的问题与独立核对

用户原话：“发现两处需要补清的执行问题。第一，历史报告中的双臂保守投影约为 38,080 秒，超过新方案给两次运行的 18,000 秒总上限，因此旧资格 PASS 不能证明新的 9,000 秒单次上限可行。第二，九次复验统一开放后的集中评价，需要明确计入哪段预算，不能漏计，也不能把前八次等待其余运行的时间算成各自训练耗时。”

已核对原生result.json、native_acceptance.json、旧正式报告与实际projection/validate_gate/execute入口。保存字段为：
S_pos projected_total_seconds = 18844.60961239063；
H_pos projected_total_seconds = 19235.266476024408；
双臂合计 = 38079.87608841504。
旧双臂projection/validate_gate的时间上限为57600秒；single.projection中的单臂within_budget对应28800秒，二者均不是9000秒。旧PASS及within_budget=true保持其历史有效性，但不能作为新预算准入结果。
旧实跑双臂12661秒、除以2得到6330.5秒/次，只支持粗略耗时参照；共享装载/评价与方法差异使它不能成为每一新trial的上界。约79小时不等于45次在114小时内已经通过资格。

2. 对9000秒与114小时的明确处置

保留它们为待证实的预算提案，不称已具备执行可行性的硬限合同；当前新资源准入为未通过/未建立。没有以本补充自动扩大预算，也不将旧PASS复制为新gate。
未变的数学、梯度、恢复等证据按适用范围复用；时间资格必须针对新来源、三臂、实际阶段组成及本补充的计时边界重新判断。旧两候选投影都超过9000秒，新S也不能用两候选平均值代替自身投影。
本轮实现稿应先写清成本模型的调用次数、实测项、固定开销和未测余量，并由获准的新原生资格提供必要实测。旧保守模型中的1.25和1800秒余量不能为凑过门临时删除；若采用更贴合新入口的模型，必须在测量/正式结果前说明依据并经主审和相应审查确认，旧预测仍保留。
对每臂分别给出P_search（含本trial完整评价）和P_rep（止于盲完成并退出），覆盖获准两参数空间和固定工作量的成本依据；不能只测较快的臂或用三臂均值。对新增独立装载/读入、恢复、盲分数/诊断、保存、释放和控制成本不能漏项。
形式准入至少要求每臂P_search<=9000、P_rep<=9000，12*sum(P_search)<=324000，3*sum(P_rep)<=81000；另有本补充第4节共享阶段的投影与剩余额度约束，总投影不超过410400秒。
如果新投影仍超限，就停止在正式搜索之前，明确提出实际需要的预算/成本模型/范围修订，由用户确认；不先运行默认锚点碰碰运气，不以实际可能更快放行，不自动从其他臂、最终留出预留或旧合同余额借时间。
因此：这次补正关闭“误用旧PASS作为新资格”的解释缺口；9000秒真实可行性仍是进入正式搜索前的未解决执行前提，不伪称已经关闭。后续仅批准实现或原生资格时，也不自动批准45次训练。

3. 单次搜索与单次复验的计时终点

所有执行时间以父进程单调时钟的实际连续占用区间计，开始于启动该运行子进程之前，结束于该运行所有子工作退出且父进程确认资源释放；导入、装载、I/O、进程内阻塞及失败开销都计入，不能只加GPU kernel或optimizer时间。

搜索trial：本trial的完整A/B训练、校准、两端点/恢复、12捕获、盲门、一次valid解析、完整指标/诊断评价、所需落盘和退出均在自己的9000秒内。反馈U必须在这些操作成功完成后，不能以B末更新完成冒充trial COMPLETE。trial外部真正未重叠的ask/tell与账目维护计共享预算。

复验run：自己的训练、校准、18端点中对应的两端点/恢复、盲valid分数、12捕获、盲完整性核验、落盘及释放退出均在自己的9000秒内。退出时仅记该run盲计算完成，valid仍为0；九次复验整体尚未评价完成。每个run的时钟在它自己的盲完成并退出时终止，不等另外八次。

等待：某个已完成run等待其余run的期间，只记完成时间/评价时间之间的日历等待，不累加进该run训练时长。后续run实际执行时，只计后续run；控制器若在此期间等待子进程，不再重复计一遍。资源排队也单独报告；额外实际的非重叠控制/核验工作仍计共享预算。子进程已经启动后的慢I/O或资源争用不能伪装成可扣除的“等待”。

4. 九次集中评价明确归入现有3300秒共享预算

将原“独立控制/保存结果分析3300秒”明确改释为“所有未计入单次运行的控制、九次集中开放评价及保存结果独立分析，合计3300秒”。不是再新增3300秒，不从9个9000秒重复扣评价，也不占最终留出21600秒预留。

集中评价从九份盲完成记录/保存产物的集合核验开始计时，包含：
- 验证9次及其18端点、108捕获的完整性/身份与全体开放门；
- 一次共享valid监督解析（含失败尝试的实际接触账）；
- 全9次保存分数的所有约定指标、计数/N/A、诊断及预设比较/区间；
- 三seed聚合、六格方向判读、结果核对、写盘与评价进程退出。
只消费已保存盲分数/必要诊断及获准一次监督；不为集中评价补做模型前向、重新训练、重复train解析或载入旧Memory。必需盲预测缺失时属于运行失败，不能用共享评价预算暗补。

令C为未与任何子运行区间重叠的实际控制费用，E为集中开放/评价费用，A为独立保存结果分析费用，则C+E+A<=3300秒。三者的区间互斥；独立分析不得在C/E已计时的进程内再重复累计同一时间。
正式准入前必须给出三者的具体投影/必要预留，合计<=3300秒。不能因为旧独立分析只用了约3秒，就断言新九次完整评价也只需3秒；原native投影未自动证明此共享段可行。控制阶段必须保留尚未执行的集中评价/分析预留，不能先将额度用完再免费评价。
集中评价可用硬截止为共享剩余额度与全阶段总剩余额度的较小者。只要任何上限耗尽即停止，保留已用时间、阶段状态、部分产物及valid接触；不重复开封、免费重试或拼凑“已完成”。如果3300秒的保守投影不足，须先修订提案并确认，不静默扩大或从别处挪借。

5. 总账与最小实现核验

T_development =
T_CPU + T_native + sum(36个完整搜索区间) + sum(9个复验盲计算区间) + C + E + A。
各预算仍为300 + 1800 + 324000 + 81000 + 3300 = 410400秒 = 114小时；这是无漏计/无重复的预算恒等式，不代表资源可行性已经证明。失败与进程内阻塞计入所属区间。排队/外审/等待用户等另报日历时间，不据此宣称任务会在114小时的连续日历内结束。
九次复验“训练盲计算全完成”“统一开放评价完成”“独立分析完成”分别记录，最终完成必须覆盖全部阶段。

未来只在已有增量计时/编排核验中增加能发现这两个缺口的例子：
- 数学/恢复PASS但P_search或P_rep>9000时，新的正式入口必须拒绝；
- 前八次已经退出后推进至第九次，前八次账保持不变；集中评价只计共享一次；
- 集中评价从剩余共享额度扣费，超时/失败保留账且不标整体完成；
- 控制器等待与子运行重叠不能双计，实际评价/分析不能漏计。
这些是待实现行为要求，当前未运行测试、Linux资格、指标重算、训练或新数据读取。无需新增通用计费框架或重跑未变数学证据。
