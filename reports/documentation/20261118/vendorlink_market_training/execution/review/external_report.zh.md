### 2. 三条反传没有被替换成“只更新辅助分类头”

**当前域监督。** `AccountModel.backward_h()` 先在真实记录表示上计算自然/重组 H 监督对 pair-table 的梯度，再用 `pair_backward()` 对同一关系头分块反传；当前 CE 对同一记录 leaf 反传，最后 `z.backward(leaf.grad)` 回到当前编码器或当前银行。定位：`source/step35_vendorlink_account_methods.py:63–117`。

**旧群标签。** `MarketH.backward_h()` 检查该群确属已完成市场，并按出生市场路由，传入 `frozen_history=True`。底层要求历史 `z` 不带编码器梯度图，但关系头仍参与 `pair_backward()`，所以旧标签能更新共享关系头，同时不能更新旧基座、旧银行或错误地更新当前银行。定位：`source/step35_market_adapters.py:99–103`；`source/step35_vendorlink_account_methods.py:103–107`。

**确定性出生保持。** `backward_birth()` 用自然账号聚合后的分数计算独立的 `β × MSE`，教师 detached；`deterministic_student()` 临时关闭 dropout，并保存/恢复 CPU、CUDA RNG。Full 的旧标签分支先按 ER 设置计算，随后单独调用出生分支，避免保持项重复计入，也没有把 β 再乘 α。定位：`source/step35_vendorlink_account_methods.py:16–34,69–70,119–142,165–171`；H 目标原公式见 `source/unchanged_excerpts.txt:19–41`。

### 3. CUDA 检查点故障有针对性修复，当前重算作用域正确

`run.make_model():57–61` 启用非重入检查点 `use_reentrant=False`。`MarketH.backward_h()`、`backward_birth()` 的路由上下文包住整个底层调用，包括实际 `z.backward()`，直到反传返回才恢复旧路由。当前 `MarketRoute` 是模型对象状态，不再依赖 CUDA autograd 工作线程无法继承的 `ContextVar`。定位：`source/step35_market_adapters.py:34–55,99–109,148–160`。

这条实现成立的前提是**每个 worker 串行调用自己的模型**；当前代码满足该前提。没有必要为了未计划的同模型并行反传改造一套通用路由平台。

GPU01 记录的错误发生在第一次 CUDA checkpoint 反传、优化器之前。`gpu01_disposition.json` 保留了首次失败和 **6 秒**费用，将原先前向前记下的 `optimizer_intents=1` 纠正为实际 optimizer 入口 **0**。GPU02 改为主 AdamW 的 step hook，完成 **12 次**实际入口。因此不能简单把两个 intent 字段相加，宣称发生了 13 次真实更新。

**证据边界：** 本包给的是匿名化回执与处置，没有 GPU01 原始完整错误栈。我能核对其故障位置与实际源码执行顺序，并确认 GPU02 当前源码身份一致，不能声称亲自读过未提供的原始日志。

## 三、问题二：六群、配对、1 MiB、四端点与资源证据

### 1. 六槽和配对流按原机制进入实际训练

`source/unchanged_excerpts.txt:69–113` 的 Memory 是原 Algorithm R：按 uid 排序候选，累计 `seen`，用私有 RNG 作六槽替换，只为新存活群生成教师，旧教师不刷新；保存内容含记录、出生阶段、教师、`seen` 和 RNG。`source/step35_vendorlink_account_run.py:124–156,199–207` 只用当期 fit 的 epoch 0 群作候选，只有前两阶段更新记忆，后两域每次更新抽一个旧群。

同 seed 的三组 H 使用相同当前群生成规则。ER/Full 的替换、抽样和重组随机种子与损失分支解耦；Full 的确定性分支不额外消耗配对 RNG。`source/step35_market_worker.py:29–42` 还在正式训练完成后比较三组 `current_stream`、ER/Full 的 `history_stream` 和两阶段 survivors，并核 SEQ 无历史/教师消费。**教师值不要求 ER 与 Full 相等**：两臂开始分化后，各自出生端点产生不同教师是合同允许的。

方案规定每条 H 更新 **8,160 + 2,400 + 13,080 = 23,640 次**，后两域历史抽样 **15,480 次**；每条 V 为 **23,720 次**。实际完成验收按绑定账号数和群函数重新计算曝光/更新及历史调用数，不只看退出码。定位：`source/unchanged_excerpts.txt:140–168`，对应原 `validate_training()`。

### 2. 1 MiB 检查的是完整历史包

`source/step35_market_adapters.py:194–232` 把两套银行、路由/恢复元数据和完整 `Memory.bytes()` 写入不压缩 ZIP，按整个 payload 检查 **≤1,048,576 字节**，不是只统计裸参数。SEQ 必须零群、没有 `memory.pt`；ER/Full 必须六群。`run.py:106–116,134–136` 在阶段末、进入 B 和复制 C 后实际执行该检查。

**本问放行意见：配对流、总帽、SEQ 零群和端点恢复路径有条件通过；真实文本包大小、全市场评分规模和并发峰值仍由正式运行中的既有检查约束，不能从合成资格预先保证。**

## 四、问题三：训练访问、完整身份、联合判据和一次开发开放

### 1. 当期 fit、九格盲评分与 confirm 隔离

`source/step35_market_worker.py:112–144` 要求固定部署的 gate，worker 必须是原控制器的直接子进程，且核对父进程 PID、`start_ticks`、`boot_id`；任务表必须与 `market_tasks()` 完全相等。训练闭包以 `iter(DOMAINS)` 强制 A→B→C，每次先记录访问，再只读取当前 `domain:fit`。`run.execute()` 没有读取 gallery、dev 或 confirm 的调用。

`source/step35_market_queue.py:179–211,254–276` 要求十二个逻辑任务各有一个经过验收的成功尝试，完成配对流核对后才单 GPU 串行盲评分；评分齐全才分析。`worker.py:146–169` 再次校验训练身份和成功回执，正式评分硬编码 `role='dev'`。`evaluate.py:150–161,241–275` 要求九格、指定读取器、FIT12 来源齐全，分析目录新建、完整任务列表一致后，才计算全批 13 指标。

这里“盲评分”应准确解释为**不计算或反馈开发指标的评分阶段**，不是声称评分程序没有读取 dev 文本及其账号索引。真正与训练隔离的是：所有训练先结束，评分和分析结果不回流训练；本批没有确认集开放动作。通用 `score()` 支持 `confirm`，不等于本轮正式入口会调用它。

主指标也对齐方案：一个账号的两条 dev 文本形成一个 Q2 查询，用固定全市场候选稳定排序取第一名，再计算类别等权 Macro-F1；不是将两条广告分别当两个主查询，亦不是以 Top1 代替 Macro-F1。V_CLS 的广告级辅助读数另存。定位：`source/step35_vendorlink_account_evaluate.py:17–25,79–115,218–225`。

### 2. 实际新判据在 `paired_report()`，不能只审旧 `decide()`

### 2. 最小闭合工作

执行者无需重开整个历史实现审查，也无需搜索方法、调参或追加 GPU。合理的闭合范围是：

1. 修复 R01，并用上述小型 CPU 夹具验证冻结后费用、重复事件和剩余额度。
2. 修复 R02，用一份前史一致的完整假设结果和一份仅 R01 改变而科学四门仍成立的假设结果，验证解释有效性状态。保留原四门真值，证明没有偷改科学门。
3. 绑定修复后的实际生产源码与操作入口，在主审处置中明确哪些旧资格可以继承。`operations.py:175–189` 已有源码变更独立处置入口，应据实使用，不能把旧 CPU 回执改写成当前精确源码重跑。
4. 在同一冻结部署落实模型/数据绑定、最终预算与现场资源检查，再由原授权执行者启动；实际更新和进程身份确认后更新进度记录。当前授权不需要因为方案中的旧时点文字重新索取。

**最终意见：修复并独立闭合 R01、R02 后，可以按现有授权放行这一个固定四组开发批次。当前附件已提供有价值的真实工程路径证据，但尚未提供本批真实市场效果；它不能证明 Full 比 ER 少忘、四门会通过、三路吞吐达到排期，或新方法值得替换旧 ER。完整正负结果都应按原冻结判据留下；confirm 继续封存，未知跨账号同控效果不作外推。**
