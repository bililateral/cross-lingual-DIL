# 四组正式训练入口的合成核验

Linux 既有 py310 使用手写文本与既有官方 BERT，直接调用同一训练、优化、保存、恢复及 Q2/FIT12 评分入口。核验覆盖新增适配器训练路径。账号数、开发效果和本批的正式训练吞吐须由正式运行分别测量。

| 观测 | 实测 |
|---|---|
| 单核 CPU，H_SEQ | 三市场共 9 次更新，历史群消费与教师生成均为 0。冷启动及三个阶段末端点恢复后，全部九格两侧向量及实际分数逐位相同。独立的 ER 标签梯度非零，确定性出生评分保持的共享头梯度与直接计算最大绝对误差为 0，旧编码器无梯度，确定性分支 RNG 恢复。生命周期 36.615 秒，按 37 秒入账。[CPU 原件](evidence/cpu01.json) |
| 首次 CUDA，H_full | 首批进入反向重算时，CUDA 的 autograd 线程读不到线程局部市场路由。首个 AdamW 调用前退出。保留启动前意向计数 1、实际优化器进入数 0、失败费 6 秒及修复前来源 `739e2790`。[失败原件](evidence/gpu01.json) · [计数与处置](evidence/gpu01_disposition.json) |
| 修正后 CUDA，H_full | 每个单模型、顺序调用的 worker 在同步反向返回前保持同一市场路由。12 次主优化器更新、6 次历史标签及确定性出生监督、123 次按当前市场的检查点重算。最大组 44 条记录、88 路 256-token 输入。学完 A 的基座和学完 B 的旧适配器在后续阶段无漂移，共享头的 Adam 状态跨市场延续，C 从 B 独立复制后能够更新。全部九格双方向量及分数重载一致。[GPU 原件](evidence/gpu02.json) |
| 大小与资源 | 两套 FP32 适配器、六群原记录、教师、采样状态及路由身份在此次合成端点实际占 979,611 字节。1 MiB 上限为 1,048,576 字节，正式任务逐边界继续检查。整 PID 显存采样峰值 3,764,387,840 字节（3.51 GiB），按方案预留每 H 槽 5 GiB。第二次原生资格 28.579 秒，计 29 秒，含首败共 35 GPU 秒。[资源和容量](evidence/gpu02.json) |

修复只涉及单模型市场路由如何跨 CUDA 重算线程可见。原合成 CPU 证据、首败记录及其真实费用均保留。此前 OOM 手工重开槽位核验 6.09 秒按 7 秒计入辅助，与 CPU 模型核验合计 44 秒。三项均在正式四组队列之外，只使用合成输入。[原 OOM 调度回执](../oom_qualification.json)
