## 二、第一问：什么时候允许离开 VendorLink 等待

`operations.py:26–29,87–98,120–126` 在准备时校验具名英文 gate 与 launch 的预置 SHA，将 launch 的文件记录写入中文授权和 gate。`scripts/step28_benchmark_wait.py:32–75` 每轮从这个 launch 校验并读取它绑定的 gate，核协议、前序工作区与 campaign 路径、控制器 cwd 及 `campaign --gate <该路径>` 命令尾部。现场应确认固定 launch 中绑定的正是同一份具名英文 gate；包内未提供这两个实际文件。

| 观察状态 | 实际行为 |
|---|---|
| 原控制器活着，整批 completion 尚未出现 | 返回 `WAIT_VENDORLINK`。训练已完但仍在评分、评分已完但仍在分析、前序同一控制器正在等待具名 OOM 交接，均继续等。此时尚不采中文 GPU 资源，也不创建中文 campaign。 |
| 整批 `failure.json` 已存在；或没有 completion 且原控制器已退出 | 抛出技术故障。进入等待循环后的异常会留 `wait/failure.json`，记录累计活动秒及禁止自动重启。单槽已处置的历史 OOM 不等于这个整批故障。 |
| 已有 completion，但训练、评分或 dispatch 的规定字段不一致 | 拒绝交接。核对经 gate 绑定的 12 项任务、训练任务及 winners 键集合、评分任务及按序的 12 个完成路径、整批一次开 dev、confirm 仍关闭、分析决定的指定路径，以及 dispatch 为 COMPLETE、无 active、无 cleanup_errors。 |
| 整批回执被接受，原控制器或同用户带该 gate 参数的进程还活着 | 返回 `WAIT_VENDORLINK_RELEASE`。控制器按 boot ID、start ticks、owner、cwd 和完整 argv 识别，并排除僵尸。仅复用相同数字 PID 的无关进程不会被认成旧控制器。 |
| 回执被接受，上述进程均已释放 | 进入中文首槽资源检查。监听不读取科学决定值，正常负结果与正结果走相同分支。 |

原生产者也参与了这条证据链。摘录 7–40、58–86（`scripts/step35_market_queue.py`）要求四个固定方法、三个配对 seed 和三市场，验证训练成功尝试，再依次核 dev 评分和分析产物，才发布整批完成。因此正常路径比“目录里有一个 COMPLETE 文件”强。监听消费的是运营摘要：它核 winners 的键、评分回执路径及 decision 路径，没有独立验证每个 winner 的内容、评分绑定或 decision 文件的完整性。单核测试甚至以空的 winner 值和只有路径的评分项走通。它证明的是这些状态分支；实际完成性还依赖受控的正式生产者。相关进程扫描能识别原生入口携带 gate 的作业，不能据此证明任意改写命令行的后代均已释放。包内没有这样的残留实例。

**R1｜必修：成功标记发布早于末次结算。** 摘录 73–86 的 `step35_market_queue.py` 先写 `campaign/completion.json`，然后在 `finally` 调 `runner.settle_handoff(...)`。若末次结算抛错，前面的 `except` 捕不到这个异常；若进程恰在这段退出，也可能只留下完成文件。待 PID 消失，`predecessor()` 看到的仍可能是合法的 12 项回执、COMPLETE、空 active、无失败文件，从而错误放行。此反例不要求更动科学结果。

最小处置是让中文监听再核一个**结算后才成立、绑定本前序批次**的运行成功依据。对已在跑的前序，优先采用已有且可核的最终结算与成功退出证据；缺失时报告待处置，勿由“PID 已消失”推算退出码。能改生产顺序时，在结算成功后才发布最终成功标记，结算异常落技术失败。单核验证分别模拟正常科学负结果并正常结算、已写旧 completion 后最终结算抛错、写完旧 completion 即退出。只允许第一种在进程释放后放行，后两种须保留故障或未决证据。

## 三、第二问：是不是只创建一批，资源波动会怎样

**具体新 gate 的排他约束成立。** `operations.py:87–91,135–151` 拒绝占用的 gate、wait 或 campaign，并用 `listener_console.txt` 的排他创建防止重复 arm。Linux 子进程以绑定解释器、绝对脚本路径和指定 cwd 启动。`once_wait.py:3–6` 把启动时刻传入监听；`scripts/step28_benchmark_wait.py:144–164,192–209` 原子建立 `wait/`，即使此次等待失败也保留占用。条件齐备后再次校验初始 gate 文件记录、监听副本，以及 `read_gate()` 返回的来源和授权范围。同一进程直接调用 `bench.start_campaign()`，没有再启动一个中文控制器。

`verify_handoff()`（同文件 87–95）将 ready 与 wait/controller 的 gate、完整身份、当前进程命令及两个 ready 标志相互核对；`scripts/step28_history_benchmark_dispatch.py:116–136` 先做此核对及预算检查，再排他建 `campaign/`。直接调用 `campaign --gate <本次门>`，在未就绪时没有交接凭据，就绪后从另一进程调用也过不了身份核验。直接 worker/post 还须持有已建作业目录、自己的 process 回执、合法 deadline 及排他 claim（`scripts/step28_history_benchmark.py:227–244,277–302`）。历史代码兼容 listener 和 predecessor 同时缺省的另一类授权；删改**本次 gate 单边字段**会与绑定的授权不符。手动运行真正的具名监听副本本身仍要经过同一前序和资源检查。

等待中，前序 launch/gate 的读取失效会在检查时转入失败；中文 gate、科学入口来源、分析计划或监听副本变化，则至迟在双条件就绪时被复核。不要把它理解为每次睡眠期间都即时报警。交接后每次构造 worker 命令还校验 gate、授权、计划及冻结的正式来源（`scripts/step28_history_benchmark_dispatch.py:32–48,134–136`）。源码异常可在派工处留下 `shared_failure.json`。有失败证据时不应删除 `wait/` 另开一批。

**首槽准入。** `resources()`（`scripts/step28_benchmark_wait.py:78–84`）调用原资源观察器，要求至少一个可用亲和核。首槽需要 10.25 GiB 可用显存、72 GiB 可用 RAM、64 GiB 空盘保留及 8 GiB 当槽写盘余量，同时满足输出预算。准备门另载每槽整 PID 10.25 GiB、allocator 9.25 GiB、RSS 64 GiB，父子 RSS 196 GiB、总输出 320 GiB、非模型产物 8 GiB。原生控制摘录 93–170、176–208 给出了准入、运行中 PID/RSS 和磁盘的部分执行路径；并非以上每项硬限都由监听函数自行实施。中文使用 `paired_start=False, cores_per_slot=1`，上限三路，不要求三槽同时就绪。

**执行前需判清：资源回落。** 监听观察到首槽不足时写 `WAIT_RESOURCES`，睡 60 秒再查。就绪观测与正式派工不是同一次采样。若前者刚够、后者又不足，正式控制器会再做准入；摘录 210–215 明示，在无 active 且 `wait_for_resources` 为假时抛错，为真时继续等待。`scripts/step28_history_benchmark_dispatch.py:134–136` 构造 `ChineseRunner` 未显式传这个选项，包内也未给继承构造器的取值。若现场为假，中文 campaign 可能已占用，但没有首个 worker，一过性资源不足即耗掉这次启动机会。最小处置是核实冻结实现对这一状态的取值；必要时仅为获准的首槽等待显式接线。用同一正式交接与调度入口依次给出“监听够、首派不足、随后够”的合成观测，验证中间零 worker、恢复后只派一次、同一 campaign、等待费按活动时间计。顺带在仅一核/一槽可用时验证不会索引不存在的槽。现有 99→100 用例只走到了代替正式派工的回调。

**已承诺的在途占用。** 摘录 93–110、119–166 会扣已知槽未体现的 RAM、写盘余量和已声明 GPU 占用与 NVML 已见值之差；同主未知 GPU 进程会使准入等待，允许观察的异主进程其已占显存已经体现在 free 中。`operations.py:120–121` 为本批固定 `other_gpu_commitments=[]`。若现场确有具名、已承诺而未体现的其他预约，空表无法扣除，须在冻结门时如实登记或等其释放；表确实为空时该配置成立。可用一项有已见部分用量的承诺验证只扣剩余部分。无需预估其他用户未来可能申请的资源。

## 四、第三问：哪一个更新触发删除，失败后能保住什么

`scripts/step28_history_benchmark_dispatch.py:24–48` 将自删检查接到正式 runner。摘录 176–208、220–244 显示，控制器为具体 attempt 排他打开 `console.txt`，启动本批 worker，保存 boot/start、PID、owner、cwd、剥去 taskset 包装后的 argv 及任务/尝试身份，并在轮询处理退出前调用 `retire_waiter(active)`。`scripts/step28_history_benchmark.py:227–244,285–298` 中 worker 先验自己对进程预约的所有权，再独占写 claim，最后才进入训练。`scripts/step28_benchmark_wait.py:98–126` 只扫描活动 worker 的本 attempt 控制台，要求完整换行的阶段一 updates 记录、严格整数正计数、活进程身份匹配且 claim 的任务 ID 正确。单有 Popen、claim、READY 或零步日志均不触发删除。

| 方法 | 原生输出和观察器的实际判据 |
|---|---|
| trial3 H、ER0.1、Logit0.1 | 摘录 285–301 的 five 入口在 `method.update` 返回后，第 1 步及每 24 步打印 `method.spec.run_id / stage / completed`。观察器以 `bench.native(name,order,seed).run_id` 匹配原生标识。 |
| L²R、ER+GCR | 摘录 310–321 的 comparison 入口同样在更新返回后打印 `spec.run_id / stage / completed`，首步即有记录。 |
| FOREVER | 摘录 326–336 的 `log` 逐条写 `run/updates.jsonl`，控制台只在 `counts.current % 24 == 0` 时打印 `stage / counts`，没有 `run_id`。观察器只读控制台，在这条分支使用 `counts.current`。 |

**R3｜必修：补齐 FOREVER 更新的原生归属。** `first_update()` 算出了 expected，但 FOREVER 分支不使用它。该臂若最先提供能被接受的记录，真实首步可能未被观察，首个可见正计数通常是 24；即使一条同形日志携带错误的 run_id，该分支也不会拒绝。独占控制台、已核进程及 attempt 目录给正常输出提供了归属依据，目前没有实际错删证据；这些条件仍不足以证明已核对该行的原生 run_id。最小改法是使 FOREVER 的原生日志在首个真实 current 更新时带 `spec.run_id` 输出，再与其余方法一致地核验；也可读取同 attempt 的逐步回执，并通过已核 startup/spec 将首笔记录绑定到正确原生轨迹。把实际采用的标识、计数与原始行或行摘要写入首更回执。用单核同一消费路径覆盖缺失/错误 ID、零更新及正确首笔，再验第一笔之后才删除。无需改优化器或重跑 GPU。

**R4｜必修：删除已发生、末回执未写成时不能完成对账。** `retire()`（`scripts/step28_benchmark_wait.py:129–141`）校验冻结 listener 文件记录、规定路径和非符号链接，写 `wait/first_update.json`，随后 `unlink()`，最后写 `campaign/waiter_deleted.json`。正常调用第二次会因末回执存在而直接返回。被删的是 `workspace/scripts/once_wait.py`；工作副本之外的模块、回执和当前控制器均可保留。若在两个持久化步骤之间中断，可能已有首更证明但文件仍在，也可能文件已删除却缺末回执。现有代码不消费已写的首更证明；后一状态再走常规路径会因文件已不存在而无法通过 verify，写失败还可能沿监控循环成为整批故障。`operations.py:155–173` 可查看两份记录和文件是否存在，供人工判断。

最小修复是将首更记录作为可核的删除意图，绑定 gate、task/attempt、原生更新及文件记录，并增加一条只对账、不重新派工的完成路径。文件仍是获准副本才允许删除；证明匹配且该路径已不存在时，可补记“对账时已缺失”，保留原始事实；路径被替换或证明不符时留故障，不能删除新对象。测试在写首更后、unlink 后分别中断，另测副本内容变化/换成链接；恢复应无新 campaign、无重复训练、无误删且有可解释的最终回执。当前校验支持具名路径和内容绑定，附件未展示基于 inode 的并发替换保护；实际部署应使用受控目录。

**观察时序和 OOM 边界。** 控制器按活动槽遍历，记录的是“首次被观察到的真实正更新”，没有跨槽排序来证明全批物理时钟上的第一步。若 worker 在两次轮询之间更新并退出，`matches()` 会拒绝该已退出进程；有健康槽时仍可由后续真实更新触发，全部退出则可能保留副本。这是保守行为。如需从已退出 attempt 核实更新，可沿 R3/R4 的持久化证据对账，不应放宽为接受任意旧日志。

本次保留 `request-oom`（`scripts/step28_history_benchmark.py:267–276`）、同一 `OomHandoff` 和编号 1/2。第二次成功须与已释放的首次 CUDA OOM、原槽及 reopened 记录相符（`scripts/step28_history_benchmark_dispatch.py:51–99`）。54 个不同任务 ID 都有赢家才发训练完成，之后才顺序生成、确认和分析。删除一次性文件不会把等待条件再施加到每个 worker；`read_gate()` 比对 listener 记录和规定路径，正式来源集合不含这个一次性副本。包内没有使用真实一次性父进程 argv 提交并消费手动恢复请求的本轮回执，不能称它已复测。做首次交接的单核验证时，可让一槽报告模拟 CUDA OOM、健康槽继续，再提交一次具名请求，确认删后同控制器接受原槽 attempt 2、拒绝重复请求；无需新建重试机制。

`scripts/step28_benchmark_wait.py:144–189` 从副本导入正式模块前开始计时；每轮累计检查和状态写入活动，睡 60 秒的间隔免计。就绪时向上取整，若 control 初值 + 已计活动 + 120 秒达到上限即停止。`scripts/step28_history_benchmark_dispatch.py:116–137` 交接时只把该等待费加一次到 auxiliary，检查首试及后处理分桶，并保留 90 秒入口余量。摘录 260–275 的正式循环把自身活动、在途 auxiliary 预约及 60 秒清理余量纳入判断。完整训练在途预约/结算和 Ledger 内部实现未摘录，本轮沿用旧调度审查；648 小时是固定首试额度总和，不能据此保证任意多次具名重试都有余量。`operations.py:107` 提到原账本另有 30 秒尾项，本包不足以独立复算其内部入账，不能把它重复加在 146 秒初值里。

**计费边界与最小验证。** 等待中的普通异常有累计活动秒，交接失败还会记录 ready 及预期账本路径。不同失败时点的证据不相同：`main()` 初始读门/解释器检查、`wait.mkdir()` 发生在等待异常记录之前；`campaign.mkdir()` 后初始化 Ledger/runner 发生在 campaign 自身的 `try` 之前。相应失败可能只有启动控制台或 wait/failure，记录了 budget 路径也不等于账本成功创建。正常路径最终写 ready 的耗时、进入 dispatch 计时前的少量工作及部分部署/observe 操作，没有分别据实结算，依赖 60 秒运营预记覆盖。若这些活动超过预记，或故障发生在首份可结算回执之前，现有证据不足以认定完整入账。最小处置是在外层记录启动与失败的实耗，超出预记时只补差，期间不重算睡眠、已交给 Ledger 的活动或已含在 CPU 资格内的时间。可用合成时钟验证长睡眠、慢写 ready、初始验门失败和建账失败四种分支。

### 具名输入与授权

`operations.py:29,46–71` 列出的数据文件只有 `manifest.json`、`validation.json`、`groups.csv`、`train/items.jsonl` 和 `train/supervision/pairs.csv`，另接合同指定的 split_rank 预训练模型目录。这里的 `validation.json` 是冻结的验证元数据。代码检查源对象存在、拒绝已占用而解析到其他目标的目的路径，并核对 manifest、validation 两个摘要；显式链接清单未包含 valid、heldout、owners 或未来确认 pairs。`arm()` 和子进程都设置离线模型环境。准备过程只对这两份元数据做摘要；包内不能据此推断已逐字节核验所有训练载荷和预训练权重，或已经发生正式读取。

**输入现场核对。** `operations.py:47–55` 用每方法的 ABC/seed 4 配置做预检，H 进入 `b.five.config(...)`；正式 H 由 `history.Spec` 构造，训练时传给 five 入口的运行时是 `history`（`scripts/step28_history_benchmark.py:40–49,160–172`）。包内没有证明两条配置路径对 data_root 和模型归档恒等，也没有证据证明二者实际不同。最小验证是用正式 H 的配置构造路径只读元数据，核对两项与拟链接目标一致；需要时让 prepare 复用同一取值函数。如果工作区原已存在整棵数据目录的父级链接，逐项 `dest.resolve()==original.resolve()` 也可能全部通过，额外角色文件仍可见。部署时检查具名链接、父目录和模型目录实际解析目标以及额外角色入口即可；在就绪前重核这些廉价元数据可发现等待期间换链。无需读取额外角色内容。发现错误目标才阻止派工，这里没有观察到泄漏。

**R2｜必修：机器闭合条件可能误收否定主审。** `operations.py:99–105,122–131` 仅检查主审文件正文含 `START_REVIEW_CLOSED` 子串，并把资格字段作真值测试，随后冻结 `authorize_execution=True`、`approved=True`、`review_closed=True`。若主审写“START_REVIEW_CLOSED=false”，或引用“待修后才可写 START_REVIEW_CLOSED”，文本就能误过。这与用户已明确授权具体条件启动并不冲突：需要真实闭合的是这次实现审查。最小修复为从受控主审产物读取独立的结构化闭合字段，严格匹配肯定值，核其实验/修复版本，并对资格用 `passed is True`，绑定所接受主审及资格回执的摘要。负审仅引用令牌、布尔假/字符串假均不得生成可执行 gate，真实通过且版本匹配才生成。不能用本报告中出现的令牌作为闭合凭据。

**Linux 部署证据。** `operations.py:74–105,122–151,177–186` 有 Linux/解释器、部署源码逐项大小与摘要、一次性副本、operations、授权文字、方案、资格及固定前序来源检查；正式入口还核本批计划、54 条轨迹、共同 cohort、预算、来源及授权一致性。现场应取得本次修复版本的实际 source_manifest、正向主审、资格、授权/gate、production，再以具名副本和 cwd 核 armed 身份；观察时区分 wait/status、ready、首更及删除回执。包内的审查清单不能替代这些运行产物。prepare 中途可能留下已冻结 gate，arm 的 Popen 或登记失败可能留下排他控制台，甚至已有活监听而尚无 armed 记录。出现这种情况，应先依据控制台、具名进程身份、wait/campaign 状态核清是否已启动及已耗费用，再处置原批次，不能把命令报错当成可安全重复 arm 的证据。

## 六、单核证据的分量与闭合意见

`tests/test_step28_benchmark_wait.py:32–103,105–150` 与 `qualification.json` 支持两个具体结论。第一，Linux 单核上实际产生和退出的占位进程配合手写运营回执，能验证部分完成继续等、同 gate 相关进程阻止释放、已有 terminal failure 被拒、合成显存 99 不足而 100 准入、重复调用排他、无回执和另一身份交接被拒；第二次还覆盖等待中换 gate。第二，一个真实 CPU 子进程对标量执行 SGD，确认参数变化，然后手写第一臂格式的日志。零更新和错 run_id 未删，正确正计数出现后删除，子进程仍活，重复调用未再次删除。两次退出码均为 0，回执均报正式数据读取、正式训练任务及 GPU kernel 为 0。测试没有制造内核实际复用同一数字 PID，也没有运行一个得出科学负结果的 FIT12 批次；这两项判断来自身份比较及对运营字段的读取方式。

测试对正常交接替换了 `process_identity`、GPU 读数、`read_gate` 和 `start_campaign`，供删除的文件是临时文本，claim 由测试写入。没有通过实际 `operations.prepare → arm → once_wait.py → ChineseRunner → 首个正式 worker` 走完一轮，也没有覆盖 FOREVER 原生首更、资源回落、前序最终结算失败、删除中断或删后同控制器手动恢复。所需补证可以使用合成输入、占位 worker 及真实 Linux 进程/文件操作，把替身放在资源和计算边界，保留真正的入口、交接、文件与调度代码。
